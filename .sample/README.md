# .sample — 樣本圖增量工作流

版本 v1.5 ｜ 2026-11-25

這裡只解決一件事：**把「新圖」和「已經分析過的圖」徹底分開**，讓每次進場只處理增量，不重複分析、不漏圖、不把半成品誤當成已落地。

---

## 一句話流程

> 把新圖投放到 `inbox/` → 盤點路徑和 sha12 → 解析主體、場景、構圖、畫法與配色 → 和現有候選比對 → 歸檔、登記 → 沿用或更新 v4 選項 → 驗證並結案。

---

## 目錄職責

| 路徑 | 誰放 | 放什麼 | Git |
|---|---|---|---|
| `inbox/` | 使用者 | **唯一的新圖投放口**，尚未分析的圖 | 本機 |
| `batches/<YYYY-MM-DD-主題>/images/` | AI 歸檔 | 已分析完的原圖，不再變動 | 本機 |
| `batches/<YYYY-MM-DD-主題>/PROMPTS.md` | AI | 該批次的逐圖 PROMPT、風格規律、變量建議、落地狀態 | 本機 |
| `INDEX.md` | 腳本 + AI | 全部圖片的 hash 台帳、狀態、落地去向 | 本機 |
| `README.md` | 維護者 | 本工作流說明 | **入庫** |

> **圖片、台帳和處理記錄只保存在本機。** Git 在 `.sample/` 只跟蹤本 SOP。樣本掃描腳本及 v4 預設仍屬專案原始碼，可透過 Git 同步。要在另一台裝置續跑時，請把本機樣本和台帳一起移轉。

批次命名用 `日期-主題`，例如 `2026-11-22-anime`、`2026-12-03-retro-poster`。同一天多批可加後綴 `-2`。

## 狀態機

每張圖在 `INDEX.md` 裡都有一個狀態，**「分析過」不等於「已加進 APP」**，這正是最容易搞混的地方：

| 狀態 | 含義 | 誰改成它 |
|---|---|---|
| `pending` | 已登記 hash，但還沒寫 PROMPT | `samples:status --register` |
| `prompted` | PROMPT 已寫進該批次 `PROMPTS.md` | AI |
| `landed` | 變量建議已併入 `src/v4/` 的主題、共享場景庫或畫風庫 | AI |
| `verified` | 已驗證落地項目；若現有選項已覆蓋，也可驗證後直接結案，落地欄記原選項 ID | AI |
| `excluded` | 已分析，整張樣本沒有可採用的建議，結案時記錄原因 | AI |

`verified` 與 `excluded` 都是結案狀態。校驗通過且處理完畢的樣本記為 `verified`，未採用的建議寫入該批 `PROMPTS.md` 的「未落地清單」。掃描會提醒全部 `pending`、`prompted` 和 `landed` 項目，包含原圖不在本機的記錄。

## 完整流程

### Step 0｜使用者：投放
把新圖放進 `.sample/inbox/`。若剛 clone 專案，先建立這個目錄。

腳本掃描 `.sample/` 可見目錄內的 JPG、JPEG、PNG、WebP、GIF、AVIF、BMP 和 TIFF，副檔名大小寫皆可。HEIC、HEIF、SVG、JXL、JP2、ICO、PSD 和 DNG 會列在「略過的圖片格式」。這些素材適合先在本機轉成 JPG 或 PNG，再放進 `inbox/`。

### Step 1｜AI：盤點（必做，不可跳過）
```bash
npm run samples:status
```
盤點會列出未登記圖片、台帳待續跑、重複內容、已登記但仍在 `inbox/` 的檔案，以及略過的格式。先從未登記清單確認本批的**檔案路徑與 sha12**。每個 hash 選一份原圖，後續移檔及登記使用同一份清單。

首次盤點會以空台帳開始。首次成功登記時，腳本會建立本機的 `INDEX.md`。

已登記的工作按狀態續跑：

- `pending`：補完分析。原圖缺失時先找回相同 sha12 的原圖。
- `prompted`：依 `PROMPTS.md` 繼續落地。
- `landed`：核對落地記錄，補跑驗證。
- `verified`／`excluded`：已結案，可以跳過。

### Step 2｜AI：分析 + 寫 PROMPT
決定批次 ID，按照確認的清單逐張分析，在 `batches/<批次>/PROMPTS.md` 寫入當前批次內容。先按[畫法解析與去重](#畫法解析與去重)拆解樣圖，再整理可重用的英文候選。原圖仍留在原位，直到本批分析內容寫完。

### Step 3｜AI：歸檔 + 登記
以下以 PowerShell 示意。逐個移動本批清單上的原圖並傳入對應的 sha12。

```powershell
$batch = '2026-11-24-example'
$images = Join-Path '.sample/batches' "$batch/images"
New-Item -ItemType Directory -Path $images -Force | Out-Null
Move-Item -LiteralPath '.sample/inbox/example.png' -Destination $images
node scripts/scan-samples.mjs --register $batch 0123456789ab
```
macOS 或 Linux 也可逐個移檔，再以相同批次和 hash 執行 Node 指令。`--register` 核對選中的原圖位於該批 `images/` 下，並把新記錄加入逐圖明細與批次總表，初始狀態為 `pending`。寫完分析後補上對應的 PROMPT 錨點，將逐圖狀態改為 `prompted`。

### Step 4｜落地到內建預設
依 [v4 格式](../STYLE-JSON.md)維護候選。每個選項用簡短的中文 `label` 和能拼入 Prompt 的英文 `value`。

| 採用內容 | 更新位置 |
|---|---|
| 主體、動作、職業、服裝與構圖 | [內建主題](../src/v4/themes/)。在「通用」維持 `LOWER_CLOTHING` 必選、`OCCUPATION` 可選。貓狗在 `ANIMAL` 使用泛稱，以 `FUR_COLOR` 區分毛色。AJ 鞋款併入「通用」的 `FOOTWEAR`。 |
| 底景與局部裝飾 | [共享場景庫](../src/v4/scene-library.json)。底景加入 `options`，以穩定 ID 為鍵。每個底景填 `categories`，可同時屬於多類。星月或花葉可放在 `decorations` 作局部點綴，滿版紋樣則作為 `pattern` 類底景。 |
| 畫法與配色 | [內建畫風庫](../src/v4/default-styles.json)。線條、明暗、媒材和表面處理寫入同一個 `ART_STYLE.value`，可替換色調放在 `PALETTE`。 |

`categories` 控制使用者可抽取的範圍。需要橫杆的引體向上可用 `requires_all` 檢查場景物件，兩隻手已有指定位置時可用硬約束排除矛盾姿勢。魚群偏好水下場景可用 `prefer`，這樣鎖定魚群時也能試雲海等幻想場景。

將可替換的主色、背景色、點綴或黑白影調寫成 `PALETTE`。沿用或加上畫法的 `look_palette:<類別>` 標籤，再在配色選項以 `requires_any` 指向相容的標籤。新增畫法時優先沿用合適的配色，確認仍有至少兩組可生成的選擇。大多數配色作用於環境與點綴，指定的角色、服裝和鞋款顏色由主題負責。嚴格黑白或一位色等畫法會限制全圖色數，應在紀錄裡標明。

需要修訂現有畫法時沿用其 ID。內建預設有改動時，按[官方預設發布流程](../STYLE-JSON.md#官方預設更新)調整 revision 並重新匯出。只引用現有選項的樣本，在台帳記下對應 ID 即可。

要把素材或現有方案交給 AI，可用 App「風格 → 方案管理」的「导出 AI 模板」或「复制 AI 指令＋示例」，再附上本批分析和要修改的匯出 JSON。可匯入的自訂主題帶有完整的 `SCENE.options`。若有獨立畫風庫，依序匯入畫風庫和主題，核對 `style.recommended` 中的畫風 ID。「自定义填写」可在 Prompt 預覽中快速試作並鎖定當次用值。正式採用時，按上表把內容收進對應的來源 JSON，再記錄檔案、變量與選項 ID，標成 `landed`。

### Step 5｜驗證
```bash
npm run validate:presets -- --samples
npm run test:prompts
npm run build
```
用本批指定的變量核對中文標籤與實際英文 PROMPT。場景改動要核對「全部場景」和指定分類的候選，並用手動鎖定驗證必要物件及幻想搭配。畫風改動要固定一組畫法與配色確認可生成，再檢查不相容的配色會被拒絕。修改 AI 匯出示例時，可另外執行 `node --experimental-strip-types design/test-v4-examples.mjs` 檢查示例。

有出圖對照時，固定主體、場景、構圖及出圖模型。要比較畫法，就只換畫法，並選雙方都適用的配色或相近色調。要比較配色，就固定畫法只換配色。記錄線條、陰影或材質有哪些可見差異，並檢查主體特徵是否保留。若只跑過 JSON 與 PROMPT 驗證，在 `PROMPTS.md` 第五節明記「提示詞已驗證，待成圖對照」。逐圖明細全數結案後，再完成批次總表的結案標記。

## 畫法解析與去重

先描述圖上看得到的特徵，再推斷可能的畫法。像紙纖維、套印錯位、硬邊色塊是可觀察的線索。實際媒材、年代、鏡頭或製程若無法從圖上確定，就標為推測。英文 PROMPT 優先寫能重現的視覺特徵。

| 解析面向 | 記錄重點 |
|---|---|
| 線條與輪廓 | 有無描邊、線寬變化、硬邊或暈邊、輪廓如何和背景分開 |
| 明暗與質感 | 陰影分幾層、邊緣硬度、亮部保留方式、筆觸、網點、紙紋、纖維或反射 |
| 前後景處理 | 遠處如何簡化、人物與背景如何分層、同一張圖是否刻意混用不同媒材 |
| 配色 | 主色、背景色、點綴色、哪些色彩屬於角色或服裝、是否限制全圖色數 |
| 主題與構圖 | 用一兩句記錄主體、動作、場景和取景，供固定條件的對照使用 |

逐圖列出最接近的現有畫法 ID，並從上表指出差異。看完同批樣圖後，整理哪些特徵換了主體或場景仍成立，再決定落地方式。

| 差異在哪裡 | 落地方式 |
|---|---|
| 現有畫法和配色已涵蓋 | 沿用，記下對應 ID 和判斷依據。 |
| 畫法相同，只有主色、點綴色或影調不同 | 評估是否需要補相容的 `PALETTE`。 |
| 畫法相同，現有英文描述漏了關鍵可見特徵 | 補進原 `ART_STYLE.value`，沿用 ID。 |
| 換掉配色和主體後，線條、陰影組織或媒材仍有明顯差異 | 整理成一套完整的候選畫法，先做固定條件的對照。 |
| 差異在角色、職業、道具或取景 | 記為主題變量或構圖建議。 |
| 差異在環境、純色底、抽象背景、紋樣或局部裝飾 | 比對共享場景庫，記下適合的分類及已有或新添的候選 ID。 |

例如樣圖有粗細變化的墨線、平塗色層和一層硬邊陰影，先比對「90 年代手繪賽璐璐」。夕照讓背景偏橘，可以沿用暖色配色。若畫面是以吸水紙上的透明疊色和洇開的顏料邊緣塑形，再比對「濕畫法水彩」。同一畫法的線條、陰影和表面處理應放進同一段 `ART_STYLE.value`，避免拆成各自抽樣的修飾詞。

## PROMPT 保存規範

1. **一批一份 `PROMPTS.md`，不拆成單圖檔。** 17 張圖拆成 17 個檔只會讓檢索變碎；批次才是自然的分析單位，也對應一次預設改動。
2. **固定五節**。
   - 一、逐圖 PROMPT。每張列出序號、檔名、sha12、一條可複製的英文 PROMPT，並分別記錄主體與構圖、底景與裝飾、畫法與配色。
   - 二、整體畫法規律。整理跨圖共通的特徵、最接近的內建畫法 ID，以及能否靠換配色重現差異。
   - 三、v4 落地建議。記下沿用、新增、修訂或留待對照的判斷。變更片段用 `id`、中文 `label`、英文 `value` 與適用的標籤和約束。
   - 四、待辦與限制。記下樣圖無法證實的判斷、待補的對照，以及尚未落地的項目。
   - 五、落地狀態。記下檔案與選項 ID、提示詞驗證結果，以及是否做過成圖對照。
3. **雙識別**：每張圖用「檔名 + sha12」標識。檔名可能變（實測本批檔名雖是 32 位 hex，但**不是內容哈希**），只有內容 hash 是可靠的去重鍵。
4. **錨點對應**：`PROMPTS.md` 的逐圖序號（`01`…`17`）寫回 `INDEX.md` 的「PROMPT 錨點」欄，日後可從任一張圖反查它變成了哪個變量。
5. **頭部元資訊**：每個 `PROMPTS.md` 開頭標明批次 ID、圖片目錄、台帳位置、狀態與日期。

### 無主體／純背景圖怎麼處理

樣本裡可能出現沒有角色、只有圖形／景物／紋樣的概念圖。**不要因為「沒有角色」就整張丟掉**：

- 記下可見母題、場景與構圖。角色欄位留空。
- 照樣解析線條、陰影、媒材與前後景，先比對現有畫法，再評估配色。
- 可重用的母題與取景可併入 [風景與背景主題](../src/v4/themes/concept.json)，底景或裝飾可更新 [共享場景庫](../src/v4/scene-library.json)。畫法與配色按實際採用項目登記與驗證。

## 防重複的三道保險

| # | 機制 | 擋住什麼 |
|---|---|---|
| 1 | **物理隔離**：`inbox` ↔ `batches/*/images` | 一眼看出哪些沒處理；AI 只需看 inbox |
| 2 | **內容 hash 台帳**：`INDEX.md` 記錄 sha256 前 12 位 | 改檔名、複製到別處、重複丟同一張圖都擋得住 |
| 3 | **掃描腳本**：`samples:status` 遍歷全目錄比對 | 圖被亂放、忘了歸檔、或以上兩道失靈時兜底 |

內容 hash 用於確認同一張圖。台帳狀態用於確認下一步，批次路徑則用於核對原圖已歸檔到哪裡。

## 指令速查

| 指令 | 用途 |
|---|---|
| `npm run samples:status` | 盤點：列出新圖 / 已處理 / 重複 / 待歸檔（唯讀） |
| `node scripts/scan-samples.mjs --verbose` | 額外列出每張已登記圖的狀態 |
| `node scripts/scan-samples.mjs --json` | 匯出機器可讀的樣本盤點，提供給 AI 判斷本批素材與台帳狀態 |
| `node scripts/scan-samples.mjs --register <批次> <sha12> [...]` | 登記該批已歸檔的明確選中圖片 |
| `npm run validate:presets` | 校驗預設 JSON（零出圖額度） |
| `npm run validate:presets -- --samples` | 執行 v4 校驗並列印各內置主題的 Prompt 範例 |
| `npm run test:prompts` | 驗證 v4 選項約束、抽樣與鎖定 |
| `npm run build` | 型別檢查與打包 |

## 常見情況

| 情況 | 處理 |
|---|---|
| 同一張圖換了檔名又丟一次 | sha12 相同 → 腳本標 ⚠️ 重複，台帳不會新增列；直接刪掉副本即可 |
| 想重新分析某張舊圖 | 保留 sha12，將逐圖與批次狀態改為 `pending`，在 `PROMPTS.md` 註記原因，再按盤點的待續跑清單處理 |
| 圖直接丟在 `.sample/` 根目錄 | 在盤點中確認路徑和格式，選進本批清單後照 Step 3 歸檔 |
| 只想看某一批 | `INDEX.md` 的批次總表 + 該批 `PROMPTS.md` 第五節 |
| 新圖和現有畫法相近 | 在第三節寫最接近的畫法 ID 和可見差異。畫法與配色都已涵蓋時，核對後沿用原選項 |
| 同一批次陸續到圖 | 用同批次 ID 和新增圖片的 sha12 登記。腳本會按台帳重計張數，並把批次狀態設為 `pending` |
