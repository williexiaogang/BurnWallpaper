## 抠像缓存语义重构：一图一结果，失败终态化

用户反馈两个问题（dev 与正式环境行为一致，非环境差异）：
1. 抠像失败的壁纸每切换一次图片就重新推理一次。
2. 切换抠像模型后所有壁纸重新抠图，没有必要。

根因：
- cutout-jobs.ts 的 pump() 只按「成功缓存」跳过，失败不进缓存；每次 syncCutoutQueue（切壁纸即触发）重置 cursor=0，失败项全部重跑。
- 缓存键与磁盘记录均按「壁纸+模型」存，换模型必 miss。

新语义：**一张壁纸只保留一份抠像结果**（记录产出模型仅供展示），换模型不重抠；失败为终态，只有用户点「重算」按钮（forceCutout）才用当前模型重算。UI 原本就有「用 X 重算」入口，无需改。

改动文件：
- src/utils/cutout-cache.ts — cutoutCacheKey/peekCutout 去掉 model 参数（保留 nonce）
- src/utils/cutout.ts — getCutout 缓存命中不区分模型
- src/utils/cutout-jobs.ts — errors 改按 wallpaperId 键；pump/publish 跳过「已成功或已失败」项；loadCutout 不带模型
- src/utils/cutout-store.ts — loadCutout(id, source) 不区分模型；浏览器 IndexedDB 单键存储 + 清理旧 per-model 键
- src/hooks/useCutout.ts — error 按 wallpaper.id 取；running 匹配只看 wallpaperId
- src/backend.ts — readCutout 去掉 model 参数
- src-tauri/src/commands.rs — read_cutout 不带 model，扫描 `{id}` 单记录 + 旧版 `{id}_{model}` 兼容迁移；write_cutout/write_cutout_raw 写单记录布局并调 remove_per_model_cutouts 清理旧文件；delete_wallpapers 原有清理逻辑不变

验证：tsc --noEmit 通过、cargo check 通过、npm run build 成功。

## 抠像队列看门狗 + 失败原因可复制

用户反馈：切换模型后回主页标签永远显示「排队抠像」；BiRefNet 失败时只能悬停看原因，没有 LOG 可复制。

根因判断：
- 队列 `pump()` 串行处理，若某个任务在 worker 内挂起（BiRefNet/WebGPU 有先例，dev 下 HMR 也可能留下已终止的 worker 单例），整条队列永久堵死，其余壁纸永远停在「排队抠像」。
- 分类失败（`outcome.error`）只写进内存 errors 表，从不写 LOG，所以「复制 LOG」里没有任何线索。

改动：
- `src/utils/cutout.ts`：任务看门狗。按模型设定停滯超时（modnet 90s / animeseg 120s / birefnet 180s，进度上报即重置）+ 硬上限，超时即回错误并 `recycleWorker()`（terminate + 重建，最多 3 次后停用）；worker `error` 事件同样走重建；worker 的 warn 日志接入应用 LOG。
- `src/utils/cutout-jobs.ts`：`runOne` 分类失败写 `logError`；`pump()` 外层加 200s 兜底 `withGuard`，防 IPC/写盘卡死堵队列。
- `src/pages/NowPage.tsx`：失败态点击从「直接重抠」改为弹出详情面板——错误全文可选中、复制原因、复制完整 LOG、用当前模型重试；标签文案改为「抠像失败 · 查看原因」。
- `src/styles.css`：新增 `.cutout-error-panel` 等样式（对齐现有扁平/等宽字体风格）。

验证：tsc 通过、npm run build 通过。

## 模型缓存读取失败导致启动重复下载

日志现象：`webgpu 初始化失败，回退 CPU：TypeError: Failed to fetch` + `默认小模型下载失败`，而 `%APPDATA%\com.burn.wallpaper\models` 下 modnet / birefnet / anime-seg 的权重明明都在。

根因：`readModel()` 用 `fetch(convertFileSrc(path))`（asset:// 协议）读本地模型。该 fetch 一旦失败（作用域/CORS 等），异常被 `resolveCacheMatch` 静默吞掉 → transformers 认为缓存未命中 → 回落到 huggingface.co 下载 → 国内网络直接 `Failed to fetch`。也就是说本地缓存从来没真正被复用过（此前能跑是因为当时能连 HF）。

另外：App 启动时无条件 `ensureModelDownloaded(modnet)`，即使已下载也要把 pipeline 重建一遍，放大了问题。

修复：
- `src-tauri/src/commands.rs`：新增 `model_read(rel) -> tauri::ipc::Response`（原生二进制响应，空 Vec 表示文件不存在），在 `main.rs` 注册。
- `src/backend.ts`：`modelReadRaw(rel)`。
- `src/utils/model-store.ts`：`readModel` 首选 raw IPC，失败才回退 asset 并 `logWarn` 留痕。
- `src/App.tsx`：启动预下载加 `warmupStarted` ref + `cutoutDownloaded.has(modnet)` 门控——已下载过就交给首次抠像懒加载，不再每次启动重建模型。

注意：Rust 命令变更需要重启 `tauri dev`（或重新打包）才生效。



## 抠像「模型已下载仍失败」的真凶：transformers 可选文件探测撞网络

用户复测（build 0944，model_read 已生效）仍报 `TypeError: Failed to fetch`。加了文件级诊断（Rust `debug_log` 命令 → data_dir/debug.log；worker 缓存命中/miss 与 env.fetch 全量追踪）后本机跑 `tauri dev` 复现，真相：

- `model_read` raw IPC 工作正常（config.json 83B 命中）——上一轮修复有效。
- 真正失败的是 transformers pipeline 创建时探测 **tokenizer_config.json**（图像分割根本用不到分词器）：本地缓存里从来没有这个文件 → 尝试 huggingface.co → 网络不通 → **fetch 挂 22 秒超时** → `TypeError: Failed to fetch` 把整个 pipeline 创建炸掉。用户日志里 21s 的间隔就是两次 22s 网络等待。

修复（`src/workers/cutout.worker.ts`）：
- `essentialsCached()`：检查 config.json / preprocessor_config.json / onnx/model.onnx（fp32）三个必需文件是否都在本地缓存。
- 必需文件齐全 → `createPipeline(offline=true)`：`env.allowLocalModels=true + env.allowRemoteModels=false`（两者不能同 false，transformers 顶层校验拒绝）。此模式下未命中缓存的文件走「本地路径探测」→ 被 fetch 包装层拦成 404 → 可选文件返回 null 秒过、必需文件抛 `ModelFileNotFoundError`，全程零网络。
- `env.fetch` 包装层：`/models/` 前缀（transformers 本地模型路径探测）直接合成 404——dev 下 Vite SPA fallback 会返回 index.html(200+HTML)，必须拦；网络失败（TypeError，被墙/离线时挂 20+ 秒）也合成 404——transformers 对 404 有优雅降级。
- 离线模式下 `ModelFileNotFoundError`（缓存清单过时）→ 放开网络重试一次。
- `classifyCutoutError` 补 404/not found 分类。
- 诊断保留：debug.log（data_dir 下，1MB 自动轮转）记录缓存决策 + fetch 追踪，排障利器。

验证：无头 Edge + 临时测试页（伪装缓存桥）端到端跑通——`local-probe→404` 拦截生效、必需文件全本地加载、CPU 推理 + 遮罩合成 SUCCESS（10MB PNG），全程零外网请求。测试页/测试模型副本已清理。

另：本轮还确认了「一张壁纸已有磁盘抠像时启动零 pipeline 活动」——上轮的磁盘复用修复工作正常。
