## 第三輪：WebGPU 推理 + 縮略圖體系（同日，用戶仍感卡頓並問能否用 GPU）

用戶問能否調 GPU 渲染加速。結論：渲染/合成本來就在 GPU；真正能加速的是推理。實施：

- **推理接入 WebGPU（三模型統一 GPU 優先 + CPU 回退）**：
  - ORT 改根導入（`onnxruntime-web` 而非 `/wasm` 子路徑）→ jsep 加載器 → jsep wasm 是 CPU+WebGPU 超集（plain/asyncify 版不含 WebGPU EP，二進制裡 0 個 jsep 符號）。
  - 兩個 ORT 實例必須各配各的 wasm：transformers v4.3.2 自帶嵌套 ORT（1.31.0-dev，與直接依賴 1.31.1 是獨立實例），`env.backends.onnx.wasm.wasmPaths = { mjs, wasm }` object 形式（支持 mjs/wasm 兩鍵）指向嵌套包自己的 jsep 文件；直接 ORT 同理。跨版本混用 JS glue 與 wasm 有 ABI 風險。
  - `hasWebGPU()`：worker 內 `navigator.gpu.requestAdapter()` 探測，緩存結果；MODNet/BiRefNet（transformers pipeline `{ device: "webgpu", dtype: "fp32" }`）與 anime-seg（`executionProviders: ["webgpu"]`）全部 GPU 優先、失敗回退 CPU 並記日誌。
  - 順帶修掉隱患：transformers 默認 wasm 解析在 Vite 打包後 404，release 版此前靠 jsdelivr CDN 兜底（離線會壞）；顯式配置後 dev/release 一致。
- **縮略圖體系（4K 縮略圖全部換 480px webp）**：新增 `src/workers/thumb.worker.ts`（createImageBitmap resize + OffscreenCanvas webp 編碼，0.75KB chunk）、`src/utils/thumb-store.ts`（IndexedDB 持久化 + 內存 LRU 240 + object URL）、`src/hooks/useThumbnailUrl.ts`（useSyncExternalStore）。Shelf/收藏/輪換頁三處改用縮略圖，生成期間回退原圖（僅首次會話）；DesktopPreview 保留原圖。刪除壁紙時 dropThumb 清理。
- **Vite 插件 pruneDeadOrtWasm**：剔除 dist 裡死重 asyncify wasm（26.9MB，被 jsep 覆蓋後無引用，Vite 對 new URL 靜態引用照單全收）。產物 wasm 從 41.7MB → 57.9MB（兩套 jsep 是 WebGPU 的代價）。
- 打包產物現狀：cutout.worker 978KB（根 ORT 含 webgpu glue）、thumb.worker 0.75KB、主 bundle 361KB。

注意：用戶若仍覺得卡，建議用 `npm run tauri build` 的 release 版判斷（dev 模式 React 雙渲染 + 未壓縮，本身慢不少）；驗證 GPU 是否生效看 devtools 裡 `[cutout-worker]` 的 "webgpu 可用" 日誌。

## WebGPU 報錯修復：jsep → asyncify 變體錯配（同日深夜）

症狀：啟動即報 `[cutout] 默认小模型下载失败 — no available backend found. ERR: [webgpu] TypeError: ht(...).webgpuInit is not a function`。

根因（重要經驗，之前的判斷是錯的）：
- ORT 1.31 的 WebGPU 走 **asyncify 構建**，不是 jsep。`webgpuInit` 定義在 asyncify mjs 膠水裡；完整 WebGpu EP（WebGpuContext/ExecutionProvider/ContribKernels）只編譯進 asyncify wasm（jsep wasm 只有 3 個 webgpu 字符串殘跡）。
- transformers 4.3.2 內聯的 ORT 膠水引用 `ort-wasm-simd-threaded.asyncify.mjs/.wasm`；上一輪把 wasmPaths 指到 jsep 文件 → 模組無 webgpuInit → 報錯。
- `onnxruntime-web` 根導入 default 是 `ort.bundle.min.mjs`（jsep 路線，417KB）；**`/webgpu` 子路徑**才是 asyncify 路線（`ort.webgpu.bundle.min.mjs`，僅 122KB）。
- getPipeline 的 CPU 回退沒顯式 device:"wasm"，transformers 默認設備解析在 WebGPU 環境下會再選 webgpu，同樣的錯誤二次拋出成為最終錯誤——回退必須顯式指定。

修復（cutout.worker.ts + vite.config.ts，構建通過）：
- 直接 ORT：`import * as ort from "onnxruntime-web/webgpu"` + wasmPaths 指向 1.31.1 的 asyncify mjs/wasm。
- transformers：`env.backends.onnx.wasm.wasmPaths` 指向嵌套 1.31.0-dev 的 asyncify mjs/wasm。
- 回退顯式 `device: "wasm"`。
- vite 插件反轉：剔除 jsep 死文件（regex `ort-wasm-simd-threaded\.jsep-[^/]*\.(wasm|mjs)$`），asyncify 是必要文件。
- 產物變化：worker chunk 979KB→685KB；jsep 資產（2×~29MB wasm）全部消失；dist 只剩兩對 asyncify（mjs 53KB + wasm 26.9/28.7MB）。驗證：worker chunk 含 webgpuInit×4、僅 asyncify 引用、jsep 零引用。
